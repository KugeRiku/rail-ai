# 鉄道撮影支援AI ハッカソン版 仕様書

## 1. プロジェクト概要

### 1.1 仮名称

**RailShot AI**

※名称は後から変更可能。

### 1.2 コンセプト

鉄道写真を撮影したいユーザーに対し、

**「撮りたい列車・時間・条件から、いつ・どこへ行けばよいかを逆算するAI撮影支援システム」**

を提供する。

通常の乗換案内や列車位置表示では「駅」を中心に情報を探すが、本システムでは**線路上の任意地点**を中心として列車情報を検索できることを特徴とする。

---

# 2. 解決する課題

鉄道写真を撮影するとき、ユーザーは以下を個別に調べる必要がある。

* 撮りたい列車がどの路線を走るか
* 何時に各駅を発着するか
* 駅と駅の間の撮影地点を何時ごろ通るか
* 希望時間帯にその地点をどの列車が通るか
* 撮影地点までどの程度移動する必要があるか
* 光線条件がよい時間はいつか

特に駅間の撮影地点については、駅時刻表から通過時刻を自分で推測する必要がある。

本システムではこれらを統合し、

**「場所→列車」**
と
**「列車→場所・時刻」**

の両方向から検索可能にする。

さらにAIを利用して自然言語による撮影条件を理解し、撮影プランそのものを提案する。

# 7. 通過時刻推定アルゴリズム

## 7.1 基本方式

GTFS等から以下を取得する。

* 列車の経路
* 各駅座標
* 各駅発着時刻
* 列車ID

ユーザーがクリックした位置を線路形状上の最近傍点へ変換する。

例：

A駅
12:00

↓

撮影地点

↓

B駅
12:10

A駅からB駅までの線路距離を `D` とする。

A駅から撮影地点までを `d` とする。

比率

`r = d / D`

を求める。

通過時刻は、

`A駅時刻 + (B駅時刻 - A駅時刻) × r`

で推定する。

---

## 7.2 例

A駅〜B駅：

10 km

所要時間：

10分

撮影地点：

A駅から4 km

の場合、

`4 / 10 = 0.4`

なので、

`10分 × 0.4 = 4分`

となり、

A駅を12:00に出発した列車は

**12:04ごろ**

撮影地点を通過すると推定する。

---

# 8. 精度について

列車は駅間を完全な等速では走行しないため、計算結果は厳密な通過時刻ではない。

UIでは必ず、

**「推定」**
または
**「ごろ」**

と表示する。

例：

`14:07ごろ`

将来はリアルタイム列車位置データを利用して補正可能な構造にする。

---

# 9. GTFSデータ

最低限以下を利用する。

* `routes.txt`
* `trips.txt`
* `stop_times.txt`
* `stops.txt`
* `shapes.txt`
* `calendar.txt`
* `calendar_dates.txt`

可能であれば `shape_dist_traveled` を利用する。

存在しない場合は駅座標をshapeへ投影して距離を計算する。

---

# 10. GTFS時刻の注意

GTFSでは日付をまたぐ列車について、

`25:10:00`

のように24時を超える値を持つ可能性がある。

そのため内部では時刻を単純なJavaScriptのDateだけで扱わず、

**営業日の0:00からの経過秒数**

として扱える実装にする。

例：

* 23:30 → 84600秒
* 24:30 → 88200秒
* 25:10 → 90600秒

---

# 11. 車両形式情報

GTFSだけでは車両形式を取得できないケースがあるため、独自データを持つ。

例：

`vehicle_assignments.csv`

```text
trip_id,vehicle_series,display_name,confidence
trip_001,Series-A,特急車両A,confirmed
trip_002,Series-B,通勤車両B,confirmed
```

ハッカソンではデモ対象列車についてのみ手動登録してよい。

情報が保証できない場合は、断定せず、

* 予定
* 推定
* 不明

を区別する。

---

# 12. 撮影地点データ

AI撮影プランナーでは、線路上のすべての地点を無条件に推薦しない。

ハッカソン版では、事前登録された撮影候補地点を使用する。

`shooting_spots.json`

例：

```json
{
  "id": "spot_001",
  "name": "撮影地点A",
  "latitude": 35.000,
  "longitude": 139.000,
  "nearestStation": "A駅",
  "walkMinutes": 8,
  "cameraBearing": 270,
  "notes": "公道上から撮影可能"
}
```

これにより、

* 私有地
* 立入禁止区域
* 線路内
* 危険箇所

などをAIが不用意に推薦することを防ぐ。

# 13. AI撮影プランナー

## 13.1 入力例

ユーザー：

「明日の午後、特急車両Aを撮りたい。駅から10分くらいまでで、できれば光がきれいな場所がいい」

AIは自然言語を次のような構造化データへ変換する。

```json
{
  "vehicleSeries": "Series-A",
  "date": "tomorrow",
  "startTime": "12:00",
  "endTime": "17:00",
  "maxWalkMinutes": 10,
  "lightingPreference": "good"
}
```

# 14. AIと通常プログラムの役割分担

## AIが担当すること

* 自然言語理解
* 曖昧条件の整理
* 条件の構造化
* 推薦結果の説明

## AIに担当させないこと

* 鉄道時刻計算
* 距離計算
* 通過時刻補間
* 日付判定
* 列車検索
* 太陽位置計算
* 数値ランキング

これらは通常の決定的アルゴリズムで実行する。

つまり、

**AIが答えを想像するのではなく、AIが検索条件を作り、正確な計算エンジンを利用する。**

---

# 15. AIプランナー処理

```text
自然言語
   ↓
LLM
   ↓
構造化検索条件
   ↓
列車DB検索
   ↓
候補列車抽出
   ↓
撮影地点DB
   ↓
時間・距離・光線スコア計算
   ↓
ランキング
   ↓
LLMによる説明生成
```

LLM自身に存在しない列車や時刻を生成させない。

---

# 16. 撮影地点ランキング

候補地点ごとにスコアを計算する。

例：

```text
総合スコア =
列車条件一致度
+ 時間条件
+ 徒歩条件
+ 光線条件
```

初期版では単純な点数制でよい。

例：

* 対象列車が通過：必須
* 時間帯一致：+40
* 徒歩10分以内：+30
* 光線良好：+30

---

# 17. 光線判定

余裕があれば実装する。

撮影地点の、

* 緯度
* 経度
* 日付
* 時刻

から太陽の方位角・高度を計算する。

さらに線路方向または事前登録したカメラ方向と比較して簡易光線スコアを算出する。

ハッカソン版では、

**「厳密な写真品質判定」ではなく「撮影計画を比較する参考指標」**

として扱う。

# 26. セキュリティ要件

* OpenAI APIキーをGitへコミットしない
* `.env.local` に保存
* `.env*` を `.gitignore`
* AI入力値を検証
* AIの構造化出力をスキーマ検証
* SQLへ文字列を直接連結しない
* 外部データを無条件に信頼しない
* AIに任意のOSコマンドを実行させない
* 撮影地点は安全確認済みデータのみ推薦
* 私有地・線路内・立入禁止場所を推薦しない

---

# 27. LLMコスト対策

LLMは以下の場合だけ使用する。

1. 自然言語→構造化条件
2. 最終推薦理由生成

鉄道検索そのものではLLMを呼び出さない。

同じ条件の解析結果はキャッシュ可能な設計とする。

デモでは必要以上に複数回LLMを呼ばない。

# 32. 最重要方針

**機能数より、3分間で確実に動くことを優先する。**

全国対応を急がない。

AIに計算をさせない。

確定情報と推定情報を区別する。

鉄道情報を「見る」だけでなく、

**撮影というユーザーの目的をAIが完遂するプロダクト**

として完成させる。
