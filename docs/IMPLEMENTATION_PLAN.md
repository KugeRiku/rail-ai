# RailShot AI 実装計画

## 1. 目的とスコープ

RailShot AIは、撮りたい列車・時間・条件から「いつ、どこへ行けば撮影できるか」を逆算する鉄道撮影支援AIである。ハッカソン版は、PC横長画面で行う3分デモが最初から最後まで安定して成立することを最優先とする。

MVPは1路線に限定し、最低5駅、10列車、特徴的な車両1〜2種類、安全確認済み撮影候補3地点以上を用意する。全国対応、完全なリアルタイム追跡、SNS、投稿、課金、網羅的な車両運用は対象外とする。

## 2. 要件整理

### 2.1 P0: 鉄道撮影検索の中核

- MapLibre GL JSの地図に対象路線、駅、撮影地点を表示する。
- 地図上の任意地点を選択し、最寄りの対象shapeへスナップする。
- 選択地点を通る列車を指定時間帯で検索し、推定通過時刻順に表示する。
- 列車を選ぶと、停車駅、経路、選択地点の推定通過時刻を表示する。
- 通過時刻はshape上の区間距離比で補間し、必ず「推定」または「ごろ」と明示する。
- GTFSの24時超時刻と営業日カレンダーを正しく扱う。
- 鉄道データはローカルSQLiteから取得し、デモ時に外部ネットワークへ依存しない。

### 2.2 P1: AI撮影プランナー

- 自然言語を、日付、時間帯、列車/車両条件、最大徒歩時間、光線希望等の検索条件へ構造化する。
- 検証済み条件だけを決定的な検索エンジンへ渡す。
- 事前登録された安全な撮影地点だけを候補にする。
- 候補抽出、時刻・距離評価、ランキングは通常プログラムで行う。
- 必要なら、確定済み候補データだけを根拠として推薦理由を生成する。

### 2.3 P2: デモ品質の強化

- 車両形式と、その確度（確定、予定、推定、不明）を表示する。
- 単純で説明可能なスコアリングと、任意で太陽位置による参考光線スコアを追加する。
- Loading、Error、空結果、選択状態を磨き、デモ操作を安定させる。

### 2.4 P3: ストレッチ

- 時間スライダー、走行アイコン、天気、画像入力、移動時間、複数路線、リアルタイム補正。
- P0とP1の完成・テスト・デモリハーサル後にのみ着手する。

## 3. 推奨アーキテクチャ

### 3.1 全体構成

Next.js App Routerを使う単一TypeScriptアプリとし、デプロイと3分デモの運用を単純化する。一方、内部では次の境界を維持する。

```text
Browser UI (React + MapLibre)
        |
        v
Next.js Route Handlers
        |
        +--> Application services
                 |
                 +--> Deterministic domain logic
                 |      - GTFS time/service-day handling
                 |      - shape snapping/distance interpolation
                 |      - train search/ranking
                 |
                 +--> SQLite repositories
                 |
                 +--> Server-only OrcaRouter adapter
                        - request parsing
                        - optional explanation
```

Route Handlerは入力検証、認証/制限、レスポンス整形に集中させる。計算をRoute HandlerやReact Componentへ埋め込まず、純粋なTypeScriptのドメイン関数とアプリケーションサービスへ分離する。これにより時刻、補間、検索をSQLiteやLLMなしで高速に単体テストできる。

### 3.2 採用候補

- Next.js App Router / React / TypeScript
- MapLibre GL JS（React統合は小さな自前Client Component、または必要性を確認して薄いラッパーを選ぶ）
- SQLite（Node.js runtimeのサーバー専用リポジトリからアクセス）
- Turf.js（最近傍点、線上距離等。単位とshape方向はドメイン層で明示する）
- Zod（API入力、GTFS補助データ、LLM出力）
- OpenAI互換クライアントをOrcaRouter向けに設定、または互換HTTP APIを薄いアダプターで呼ぶ
- Vitest（純粋関数/APIサービス）、Testing Library（主要UI）、Playwright（3分デモの代表導線）

SQLiteドライバーとMapLibreのReact統合方法は、実装開始時に利用するNext.js/Node.jsのバージョン、実行環境、ライセンスを確認して最終決定する。

### 3.3 データ設計

- `routes`、`trips`、`stops`、`stop_times`、`shape_points`、`service_calendars`、`service_exceptions` をGTFSから取り込む。
- `stop_times` の到着/出発は営業日0:00からの経過秒数で保持する。
- `shape_dist_traveled` があれば正規化して使い、なければstopをshapeへ投影して累積距離を算出する。
- `vehicle_assignments` はデモ対象だけ手動管理し、confidenceを必須にする。
- `shooting_spots` は安全確認済み地点だけを登録し、徒歩分数、カメラ方位、注意事項、安全確認状態を保持する。
- DBはGTFSインポート処理で再生成可能にし、アプリ実行中は読み取り中心にする。

### 3.4 API境界

仕様記載のAPIを基準にする。

- `GET /api/routes`
- `GET /api/routes/[id]/shape`
- `POST /api/passages`
- `GET /api/trips/[tripId]`
- `POST /api/trips/[tripId]/passage`
- `POST /api/ai/parse-request`
- `POST /api/planner/search`

すべての動的入力をZodで検証する。日付と営業日、タイムゾーン（MVPは対象路線の固定タイムゾーン）を明示し、SQLはパラメーター化する。エラー形式を統一し、Loading、Error、空結果をUIで区別できるようにする。

## 5. 段階的な実装フェーズ

### Phase 0: 基盤と意思決定

作業:

- Next.js + TypeScriptの最小構成、package manager、Node.jsバージョンを固定する。
- lint、型チェック、Vitest、最小CIを構成する。
- `.gitignore` と値なしの `.env.example` を作り、秘密情報と生成DBを除外する。
- 使用する1路線とGTFS/デモデータを決定し、出典・利用条件・タイムゾーンを記録する。
- APIエラー形式、座標/距離単位、営業日の定義をADRまたは短い設計文書で固定する。

完了条件:

- 空のアプリが起動し、lint、型チェック、テストが成功する。
- データ利用条件と、デモが必ずヒットするシナリオが決まっている。

### Phase 1: GTFS取り込みと決定的な時刻基盤

作業:

- GTFS必須ファイルを検証しSQLiteへ取り込む再実行可能なスクリプトを作る。
- `HH:MM:SS` を営業日経過秒へ変換し、24時超時刻を保持する。
- `calendar.txt` と `calendar_dates.txt` から対象日の有効serviceを決定する。
- 車両割当と撮影地点の補助データを検証・投入する。

完了条件:

- 1路線、5駅以上、10列車以上、撮影地点3件以上を検証できる。
- `12:00`、`23:59`、`24:30`、`25:10` と営業日例外の単体テストが通る。

### Phase 2: 地理計算と通過時刻エンジン

作業:

- shapeをGeoJSONへ変換し、クリック点を最寄りshapeへスナップする。
- 前後駅とshape上の累積距離を特定し、距離比で通過時刻を補間する。
- `shape_dist_traveled` がないデータの投影・累積距離処理を実装する。
- ゼロ長区間、shape不整合、駅順序不整合、路線から遠すぎるクリックを明示的に扱う。

完了条件:

- 駅直上、25%、50%、75%、次駅直前の期待値がテストで固定される。
- 計算結果がLLMやネットワークへ依存しない。

### Phase 3: P0 API

作業:

- 路線、shape、通過列車一覧、列車詳細、単一列車の通過推定APIを実装する。
- Zod入力検証、パラメーター化SQL、統一エラーを実装する。
- 時間内/外、0件、複数件、日付またぎを統合テストする。

完了条件:

- 仕様のP0 APIがローカルDBだけで応答する。
- 代表データでクリックから検索結果まで原則1秒以内となる。

### Phase 4: P0 地図・検索UI

作業:

- PC横長の地図65〜70%、情報パネル30〜35%の画面を作る。
- 路線、駅、選択点を表示し、クリック、スナップ、通過列車一覧、列車詳細を接続する。
- 選択列車の経路を強調し、推定表記を徹底する。
- Loading、Error、空結果、再試行を実装する。

完了条件:

- デモの「地点から列車」と「列車から地点・時刻」の両導線を完走できる。
- API障害時にも画面全体が壊れない。

### Phase 5: OrcaRouterによる自然言語構造化（P1）

このフェーズで初めてLLMを導入する。

作業:

- サーバー専用OrcaRouterアダプターを作り、Base URL `https://api.orcarouter.ai/v1`、model `orcarouter/auto`、`ORCAROUTER_API_KEY` を使用する。
- `POST /api/ai/parse-request` だけから呼び、入力長と対象フィールドを制限する。
- 構造化条件スキーマを定義し、LLM出力をZodで検証・正規化する。
- 相対日付は、LLMの自由な計算結果を採用せず、基準日・対象タイムゾーンを使う決定的処理で確定する。
- 不正JSON、スキーマ違反、タイムアウト、429、5xxを安全に表示する。
- 正規化入力のキャッシュ境界と、用途・リクエストID・モデル・レイテンシ・token usage・cache hit・成否の構造化ログを実装する。プロンプト本文と秘密情報は記録しない。

完了条件:

- 代表的な自然言語が検証済み条件へ変換される。
- 不正なLLM出力が検索エンジンへ到達しない。
- OrcaRouter側ログと照合して実測コストを説明できる。
- OrcaRouter停止時もP0の地図検索は利用できる。

### Phase 6: 決定的な撮影地点推薦（P1）

作業:

- 検証済み条件から候補列車と安全確認済み撮影地点を抽出する。
- 通過有無を必須条件とし、時間帯、徒歩分数等を明示的な重みで採点する。
- `POST /api/planner/search` とランキングUI、地図上の候補表示を実装する。
- スコア内訳と除外理由を返し、同じ入力は同じ結果になるようにする。

OrcaRouterの利用:

- 候補抽出とランキングには使用しない。
- 推薦理由が必要な場合だけ、上位候補の検証済み事実を最小限渡して説明を生成する。
- デモ安定性とコストを優先し、テンプレート説明へフォールバックできるようにする。

完了条件:

- 仕様の代表入力で必ず候補が返り、地図とランキングが一致する。
- LLMなしでも候補、時刻、順位、スコア根拠が得られる。

### Phase 7: P2の選択的強化

作業候補:

- 車両形式とconfidence表示。
- 太陽方位・高度とカメラ方位を使う参考光線スコア。
- パネル遷移、アクセシビリティ、視認性、デモ用プリセットの改善。

完了条件:

- P0/P1のテストと3分デモを悪化させない機能だけを残す。
- 光線評価を事実や保証として断定しない。

### Phase 8: リリース判定とデモ固定

作業:

- 代表導線のE2E、型チェック、lint、全テストを実行する。
- APIキー、`.env*`、DB一時ファイル、ログの秘密情報混入を検査する。
- ネットワークなし（P0）、OrcaRouter失敗、空結果の挙動を確認する。
- 3分デモを複数回リハーサルし、使用データと入力文を固定する。
- LLM呼び出し件数、token usage、OrcaRouterログの照合方法を審査説明用にまとめる。

完了条件:

- `docs/SPEC.md` 31章の12項目をすべて確認できる。
- 3分デモを最初から最後まで安定して再現できる。

## 6. OrcaRouterを利用する箇所

OrcaRouterはPhase 5以降、次のサーバー側処理にだけ使用する。

1. `POST /api/ai/parse-request`: 自然言語を構造化検索条件へ変換する。
2. Phase 6の任意処理: 決定的な検索・ランキング後、検証済み事実に基づく推薦理由を生成する。

鉄道検索、営業日判定、時刻補間、距離計算、候補抽出、光線計算、ランキングには使用しない。ブラウザからOrcaRouterを直接呼ばず、すべてサーバー専用アダプターを経由する。

## 7. 技術的リスクと軽減策

| リスク | 影響 | 軽減策 |
| --- | --- | --- |
| GTFSのshapeとstop順序・距離が不完全 | 誤った区間や通過時刻 | インポート時検証、既知地点fixture、`shape_dist_traveled` 不在時の投影、異常データの明示的除外 |
| 24時超時刻、営業日例外、タイムゾーン | 日付境界で誤検索 | 経過秒表現、固定路線タイムゾーン、calendar/calendar_datesテスト |
| 等速補間の限界 | 実通過時刻とのずれ | 常に「推定/ごろ」表示、精度を保証しない説明、将来補正可能な境界 |
| クリックが別shape/方向へスナップ | 関係ない列車を表示 | 対象路線制限、最大スナップ距離、shape/direction識別、選択結果の可視化 |
| Next.js実行環境とSQLiteの非互換 | ビルド/デプロイ失敗 | Node.js runtime固定、Phase 0でドライバー検証、デモはローカル優先。ホスティング時は読み取り専用同梱DBか永続ストレージを別途検証 |
| MapLibreのSSR/バンドル問題 | 初期表示失敗 | 地図を限定的なClient Componentにし、ブラウザ依存コードを分離 |
| 地図タイルやLLMのネットワーク障害 | デモ中断 | 鉄道検索はローカル、LLM失敗を局所化、テンプレート説明、タイルの利用条件・オフライン方針を事前確認 |
| LLMの不正・幻覚出力 | 存在しない条件や危険な推薦 | Zod検証、許可済み列挙値、撮影地点allowlist、検索・順位は決定的処理 |
| OrcaRouterの利用量/コスト把握不足 | 審査で説明不能 | 相関IDとusageの構造化ログ、OrcaRouterログ照合、キャッシュ、呼び出し箇所を2用途に限定 |
| 撮影地点の安全性・情報鮮度 | 利用者の危険 | 事前確認済み地点のみ、注意事項/確認日を保持、断定を避ける |
| スコープ膨張 | 必須導線が未完成 | Phaseゲートを守り、P0→P1→P2の順で完成判定、P3は最後まで任意 |

## 8. 各フェーズ共通の確認

- 変更範囲の単体/統合/E2Eテスト、型チェック、lintを可能な範囲で実行する。
- 既存のデモ導線を再確認する。
- 秘密情報、個人情報、未検証の外部データが追加されていないことを確認する。
- 実装内容、確認コマンド、結果、残課題を報告し、次フェーズを自動的に先取りしない。
